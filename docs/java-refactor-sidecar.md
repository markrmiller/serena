# Java refactoring sidecar

For the V2 preview-first session tools and operation matrix, see [Java refactor V2 sessions](java-refactor-v2.md).

Serena's Java refactoring sidecar is an optional LSP-mode extension for compiler-backed Java refactorings. It is separate from the existing Java language-server path: Java navigation, diagnostics, rename, and fallback behavior continue to use Serena's normal JDTLS/LSP implementation until a dedicated `java_refactor_*` tool is called.

The sidecar protocol supports lifecycle/status, semantic analysis, and preview/apply planning:

- `initialize` receives the project context as a nested `params` object: `projectRoot`, `encoding`, optional `javaHome` (echoed back in `status`), configurable `ignoredPatterns` (directory names pruned during source discovery), a structured `config` object (build-tool + analysis settings), and `projectDataDir`. A legacy flat `configuration` JSON string is still accepted for backward compatibility; the structured `config` is overlaid over it, then the top-level `encoding`/`ignoredPatterns` overlay their keys.
- `status` reports readiness, protocol version, project root, and startup diagnostics.
- `resolveTarget` and `scanReferences` expose compiler-backed symbol analysis.
- `preview` and `apply` compute structured workspace-edit plans; Python validates and applies edits transactionally.
- `shutdown` lets Serena stop the process cleanly when a project or agent shuts down.

Request lines are parsed as real JSON by the sidecar (including nested `params` payloads and escaped strings), not via regex.

The status tool is `java_refactor_status(refresh: bool = False)`. It uses Serena's normal tool execution path, so timeout behavior is governed by the existing `apply_ex` timeout handling.

Sidecar jar resolution is ordered for development and packaged installs:

1. `SERENA_JAVA_REFACTOR_JAR`
2. repo-local `java-refactor/build/libs/serena-java-refactor*.jar`
3. bundled wheel resource `serena/resources/java-refactor/serena-java-refactor.jar`

This implementation does not use JetBrains APIs. It requires Serena's LSP backend and an active project configured with the `java` language. Project discovery performs **real Maven/Gradle build-model extraction**: for Gradle, Serena invokes the project's own wrapper (`./gradlew`, falling back to a `gradle` on `PATH`) with a bundled init script that dumps each source set's resolved compile classpath, source roots, generated/annotation-processor roots, and per-source-set `release`/`source`/`target`/`encoding`; for Maven it invokes `help:effective-pom` and `dependency:build-classpath`. This yields real transitive dependency classpaths, custom source sets, multi-module structure, and per-module compiler settings rather than assumed conventional roots. Extraction is **fail-closed**: if the build tool is missing, exits non-zero, or its output is unparseable, the project model surfaces an error (`status` reports `ready: false`) so refactorings never run against an incomplete classpath. Set `allow_conventional_fallback: true` to instead degrade to conventional `src/main/java`/`src/test/java` discovery with a warning, or use `build_tool_mode: explicit` with `source_roots`/`classpath`/`module_path` to bypass extraction entirely. The sidecar configuration is sent as JSON (path lists travel as JSON arrays), so classpath/source-root entries containing reserved or path-separator characters are never truncated (including on Windows).

Scope of V1 build-model extraction: per-module source sets, real transitive classpaths, real `release`/`source`/`target`/`encoding`, custom source sets, generated/annotation-processor output roots, and — for Maven — the `maven-compiler-plugin`'s declared `<annotationProcessorPaths>` resolved to real jar paths (matched against the resolved compile classpath) and surfaced as the source set's annotation-processor path. A successful build-model extraction that resolves **no Java source sets** (an aggregator pom, a project without the java plugin, or a missed source set) is treated as a build-model error and **fails closed** by default, exactly like an extraction failure, unless `allow_conventional_fallback` is set. Deferred to a later version: Android/Kotlin source sets and live annotation-processor execution during extraction.

The Java-specific mutating tools (semantic rename, safe delete, move top-level type, inline local variable, inline constant) are marked as editing tools, so they are removed in read-only projects. They are also optional/beta tools that must be enabled explicitly; `java_refactor.enabled` gates *visibility/availability*, not just execution: in a single-project session the tools are absent from the exposed (client-visible) toolset entirely unless the project opts in, and in a multi-project / no-startup-project session — where the MCP tool schema is a fixed superset computed at session start — they stay **inactive** (calls are refused as a non-active tool) until a project with `java_refactor.enabled: true` is activated, and are withdrawn again when switching to a project without the opt-in. Targets are addressed with Serena's `name_path` + `relative_path` ergonomics (resolved to a source position via the language server); direct one-based `line`/`column` parameters remain available as an advanced path. Edit tools take `preview: bool = True` (set `preview=False` to apply) and `validate: bool = True`.

## Project configuration and routing

The sidecar is opt-in via the project `java_refactor` block. Defaults keep existing Serena/LSP behavior unchanged:

- `enabled`: enables Java refactor support. This is enforced centrally: when `enabled` is false, every semantic/mutating operation (whether invoked through a Java-specific tool *or* generic routing) refuses with code `java_refactor_disabled`. The `java_refactor_status` tool may still report a disabled/diagnostic status.
- `preview_default`: generic routed tools preview by default instead of applying.
- `java_home`, `max_files`, `max_heap`: active sidecar/runtime discovery knobs.
- `allow_incomplete_analysis`: governs the incomplete-analysis contract. When the project has unresolved compiler diagnostics (e.g. a broken or partial classpath), PREVIEW is always available with an explicit incomplete-analysis warning, but APPLY is refused (`incomplete_analysis_apply_refused`) unless this is true. With the opt-in, apply tolerates only the pre-existing diagnostics — an edit that introduces NEW compiler errors is still refused (`pre_apply_validation_failed`).
- `ignored_patterns`: directory names pruned while discovering Java sources (sent as the initialize contract's `ignoredPatterns`). An explicit list fully replaces the default `[.git, .gradle, .serena, build, target, out]`; an explicit empty list (`[]`) prunes nothing.
- `annotation_processing`: `none` (default), `classpath`, or `project`. `none` disables processing (`-proc:none`); `classpath` lets javac discover processors on the compile classpath; `project` runs only the project's declared annotation processors via a dedicated `-processorpath` (and behaves as `none` when the project declares no processors).
- `allow_conventional_fallback`: when true, fall back to conventional-layout discovery (with a warning) if real Maven/Gradle extraction fails, the build tool is unavailable, **or** extraction resolves but reports no Java source sets; default false (fail-closed). A model produced this way is flagged (`conventionalFallbackUsed`), and the apply path refuses on it (`degraded_model_apply_refused`) — preview remains available.
- `offline`: forces offline build-model extraction (Gradle `--offline` / Maven `-o`) so accidental network access fails loudly.
- `source_roots`, `classpath`, `module_path`, `release`, `source`, `target`, `encoding`: explicit project-model overrides surfaced to the sidecar's javac session (used with `build_tool_mode: explicit`, or to override extraction). Relative `source_roots`/`classpath`/`module_path` entries resolve against the project root. `encoding` is honored end-to-end (the sidecar reads sources and the applier writes edits with this charset, defaulting to UTF-8).
- `build_tool_mode`: `auto` (default), `explicit`, `maven`, `gradle`, or `plain` — forces the discovery strategy instead of auto-detecting from build files. `explicit`/`plain` bypass build-tool extraction.
- `route_generic_rename` and `route_generic_safe_delete`: opt-in routing from `rename_symbol` and `safe_delete_symbol` for `.java` files. Routing converts Serena's zero-based LSP positions to the sidecar's one-based line/column, and carries the selected symbol's identity (`nameHint`/`kindHint`/`arityHint`, derived from the LSP symbol's name, kind, and signature) so the sidecar can prove it resolved the same element (see below).
- `validate_after_preview`: when true (default), a **preview** runs the same staged in-memory javac validation as apply (the planned edit is materialized in memory and compiled, writing nothing) and the outcome is reported under the preview result's `previewValidation` key, distinct from apply-time validation. The Java-specific tools' per-call `validate` flag overrides this default for preview reporting only.
- `validate_before_apply`: when true (default), before an apply commits anything to disk the planned edit is staged in memory and re-compiled with javac; if it introduces new compiler errors the apply refuses **without writing** (`pre_apply_validation_failed`). Setting this false skips only that pre-commit step — post-apply validation with rollback always runs (see below), so a compiler-breaking edit is still rolled back; the trade-off is commit-then-rollback instead of an early nothing-written refusal. (Independently, the sidecar always validates the project *model* with javac before it plans any refactoring, so a project with pre-existing compile errors is reported via `status` rather than silently refactored; that model validation is unconditional.)
- There is deliberately **no** `validate_after_apply` knob: post-apply javac re-validation with rollback is part of the non-bypassable apply safety gate and always runs; a config containing that key is rejected at parse time.
- `include_javadocs`, `include_comments`: default values for the rename tools' per-call `include_javadocs`/`include_comments` parameters. When enabled, semantic rename additionally rewrites Javadoc `{@link}`/`{@linkplain}`/`@see` references (compiler-located DocTree edits) and best-effort plain-comment/string-literal occurrences of the old name (surfaced with a warning). Default false.
- Safe delete also exposes IntelliJ-style per-call search options: `search_in_comments_and_strings` refuses deletion when the target simple name appears in Java comments or string/character literals, and `search_for_text_occurrences` refuses deletion when it appears in non-Java project text files. Both default false to preserve the existing strict semantic-safe-delete behavior unless the caller opts into the broader textual search.
- `use_jdtls_settings`: when true (default), build-model extraction reuses Serena's Java language-server settings from `ls_specific_settings["java"]` (`maven_user_settings`, `gradle_user_home`, `gradle_java_home`, `gradle_wrapper_enabled`) so the sidecar resolves dependencies the same way the language server does. Set false to ignore those settings during extraction.

When generic routing is disabled, Serena keeps the existing LSP fallback path. When routing is enabled, sidecar refusals are returned directly rather than bypassed through LSP. Java-specific tools expose preview/apply operations directly: status, semantic rename, safe delete, move top-level type, inline local variable, and inline constant.

## Apply transaction semantics

**Preview runs the same in-memory staging/safety pipeline as apply, committing nothing.** Both stage the planned edit through the identical Python applier: paths are checked to stay within the project root, old-content hashes are verified, overlapping edits are rejected, edits are applied in descending offset order, and every text edit and file operation is materialized exactly in memory (UTF-16-aware character offsets). Hash preconditions are mandatory and fail closed: every text-edit group AND every destructive file operation (delete/rename — including a whole-file safe delete, which has no text edits) must carry the file's pre-edit `oldSha256`; a payload missing one refuses with `malformed_workspace_edit`, and a file modified between planning and apply refuses with a hash mismatch instead of overwriting the concurrent change. Any edit that cannot be staged exactly makes preview refuse (`preview_unsafe_edit`) rather than display an edit that apply would reject. When `validate_after_preview` is enabled the staged preview is also compiled with javac in memory and the outcome is reported under `previewValidation`.

Apply is transactional for **both** file I/O and semantic validity. The workspace edit either fully writes or fully rolls back on an I/O failure. After a successful write, javac always re-validates the project; if validation fails, the pre-apply snapshot is restored and the result reports `accepted: false`, `applied: false`, `rolledBack: true`, and refusal code `post_validation_failed`. Semantic renames additionally run an old-key residual check: every pre-edit reference site captured in the baseline must be **fully covered by an edit whose replacement is exactly the new name** (span overlap is not accepted as proof of replacement), the staged post-edit text at every remapped site must read the new name, and re-resolving the renamed declaration (remapped to the new file path for a top-level type rename that moved its declaration file) must yield the new name with no fewer references than the baseline — otherwise the apply refuses/rolls back with `rename_old_key_residual`.

Every javac validation response is itself gated on acceptance: a `validateEdit` call that the sidecar refuses (e.g. `project_model_errors`, `malformed_overlay`) or that fails outright carries no compiler errors and is never treated as a clean validation. The apply path refuses before writing (`pre_apply_validation_refused`, preserving the sidecar refusal under `sidecarRefusal`), a refused post-apply revalidation rolls the commit back (`post_validation_failed`), and preview validation reports `ready: false` with the sidecar refusal instead of an empty error list.

Target identity is verified end-to-end. Tools resolve `name_path` through the language server to a position and attach `nameHint`/`kindHint`/`arityHint` from the resolved LSP symbol; the sidecar re-resolves the position with javac and refuses with `target_mismatch` (before planning any edit) when the resolved element's simple name, coarse kind, or executable arity does not match — so an off-by-a-position resolution (enclosing declaration, same-line sibling, wrong overload, parameter/field name collision) can never be silently refactored as the requested symbol. The advanced line/column escape hatch carries no hints and remains position-only. Character offsets are UTF-16 code units throughout, and the applier refuses (rather than corrupts) edits whose offsets are out of bounds or split a surrogate pair, replacements that are not valid Unicode, and files/replacements the project encoding cannot decode/encode.

## Refusal reasons and limitations

The v1 sidecar is intentionally conservative and returns structured refusals instead of partial edits. Common refusal codes include `java_refactor_disabled`, `project_model_errors`, `target_not_found`, `name_conflict`, `unsupported_constructor_rename`, `overrides_library_method`, `unsupported_record_component_rename`, `public_api`, `semantic_references_exist`, `method_hierarchy_relationship`, `unsupported_parameter_delete`, `parameter_in_use`, `ambiguous_multi_declarator`, `unsupported_declaration_range`, `unsupported_resource_variable`, `non_standalone_local`, `unsupported_module_info`, `module_info_package_exported`, `same_package`, `target_exists`, `ambiguous_move_target`, `target_directory_outside_source_root`, `not_effectively_final`, `not_constant`, `not_compile_time_constant`, `non_private_constant`, `unsafe_initializer`, `unsupported_initializer`, `pre_apply_validation_failed`, `pre_apply_validation_refused`, `preview_unsafe_edit`, `apply_unsafe_edit`, `target_mismatch`, `rename_old_key_residual`, `degraded_model_apply_refused`, `incomplete_analysis_apply_refused`, `malformed_workspace_edit`, and `post_validation_failed`.

Capabilities and conservative behavior:

- **Semantic rename** renames the full override/implementation group (a method plus every project method it overrides in supertypes or that overrides it in subtypes) and updates references including member references (`Foo::bar`), constructor invocations (`new Foo()`), and parameterized types (`List<Foo>`). Type renames also rewrite the type's constructor declarations and perform the top-level file rename. Parameter renames update the corresponding project-editable parameter declaration/use spans across override/interface/abstract/cross-source-set method groups; they refuse only when a related declaration is owned by a JDK/dependency method outside editable sources. Record-component rename updates the component, backing field references, accessor call sites, and explicit canonical-constructor parameter surfaces atomically. Collision detection is semantic (element-based, including inherited members), not textual. Renaming a constructor directly is refused (`unsupported_constructor_rename`) — rename the enclosing type instead, which updates constructors atomically. Renaming a method that overrides a JDK/dependency method is refused (`overrides_library_method`).
- **Safe delete** uses the javac AST declaration range (modifiers/annotations/leading comments through the full body), so multi-line declarations are removed precisely; ambiguous multi-declarator declarations are refused. A whole-file delete is planned only when the selected type is the **sole top-level type** in its compilation unit; a file containing other top-level types has only the selected declaration removed (so siblings are never deleted). Parameter deletion is supported only in the constrained safe case: the enclosing method must be `private` and must not participate in any override/interface/abstract hierarchy, and the parameter must have no semantic uses in the method body. The parameter is then removed from the declaration's parameter list (comma/varargs surgery) and from every call site's argument list; anything else is refused (`unsupported_parameter_delete` for non-private/hierarchy methods, `parameter_in_use` when the parameter is still used, including when the body cannot be located so use-analysis fails closed). A method that participates in an override/implementation relationship — or overrides a library method — is refused (`method_hierarchy_relationship`) even when it has no direct references.
- **Inline local variable** inlines a local variable declared as its own statement in a block, *including* a declaration that shares its line with sibling statements — the declaration is removed by its exact span (`localDeclarationDeleteRange`), leaving the neighbours on that line intact. Only non-block declarations are refused (`non_standalone_local`): try-with-resources resources (`unsupported_resource_variable`), enhanced-for/for-init variables, and lambda/catch parameters. It also requires an effectively-final variable (refuses reassigned variables) and refuses initializers with side effects (method/constructor calls, array creation, assignments); replacement parenthesization is precedence-aware. When inline removes the declaration, the deleted span covers the declaration statement, its own annotation lines, and a directly-attached Javadoc — but never ordinary `//` line comments or `/* ... */` block comments above the declaration, which are preserved (the same deletion-span rules as safe delete). **Inline constant** requires a Java compile-time constant (`not_compile_time_constant` otherwise); non-private compile-time constants are **preview-only** (`non_private_constant` on apply) because they may be public API or reflection targets.
- **Move top-level type** accepts exactly one of `target_package` or `target_directory` (`ambiguous_move_target` otherwise; `target_directory` outside any source root is refused with `target_directory_outside_source_root`). It rewrites the moved file's package (detected via the javac AST, not text matching) and performs the file rename, rewrites fully-qualified references using Java identifier-boundary matching (so `com.old.Foo` is not rewritten inside `com.old.FooBar`) and explicitly-imported references, and **inserts single-type imports** for unqualified same-package/wildcard usages (inbound) and for former same-package siblings the moved file used unqualified (outbound). It refuses when any `module-info.java` `exports`/`opens` the old package (`module_info_package_exported`) and refuses `module-info.java` edits.
- Annotation-processing follows the `annotation_processing` mode (`none`/`classpath`/`project`, default `none`); generated/dependency sources are discovery inputs but not edit targets; comment/string edits are performed by semantic rename only when `include_comments` (and Javadoc edits only when `include_javadocs`) is enabled, and are surfaced with a warning since they are textual rather than semantic.
- The sidecar produces fully-escaped JSON output (all control characters below U+0020 are escaped), and the in-process project-model cache invalidates on file **content hashes** (for source/build files) rather than mtime/size, so an edit that preserves a file's timestamp and size is still detected.

Known v1 limitations (non-corrupting; apply-time javac validation rolls back on any compile failure):

- Local-variable collision detection scans the whole enclosing method, so a rename that collides only with a variable in a disjoint sibling block may be refused conservatively.
- Override grouping connects methods through project types; sibling interface methods joined only by a non-project implementor may not be grouped.
- Character offsets are UTF-16 code units end to end. A `name_path` target forwards the language server's UTF-16 column unchanged to the sidecar, which re-resolves it through javac's line map (also UTF-16-code-unit based), so non-BMP/surrogate-pair content earlier on the same line (e.g. an emoji or astral-plane identifier) aligns correctly — the resolved Java symbol is the intended one. The applier additionally refuses (rather than corrupts) any edit whose offsets are out of bounds or would split a surrogate pair, and apply-time javac validation rolls back any otherwise-misaligned edit.
